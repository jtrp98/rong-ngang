# DES-019 — Review wave · QA round · Feature QA · defect packet · TP

> Budget ≤ 8 KB · เขียนโดย `system-analyst` · 1 contract · แถวใน `design\index.md`

- **Traces:** REQ-015 (AC-049–052, AC-080), REQ-011 (AC-079 ผ่าน R24), REQ-016 (AC-053–056), REQ-017 (AC-057, AC-058, AC-077), REQ-018 (AC-059–061), REQ-012 (AC-040)
- **Rule — review wave (ตัดสินด้วย code):**
  1. ผู้สมัคร = task ที่ step `awaiting-review` · จัดกลุ่มตาม Phase ใน `plan\index.md`
  2. task "ใหญ่" (diff > `largeTask.diffLines` หรือไฟล์ > `largeTask.files`) หรือ `Security-sensitive: yes` (task file — DES-014) → session ของตัวเอง
  3. ที่เหลือเรียงตามลำดับแถวในตาราง Tasks แล้ว pack ทีละตัวจนเกิน `reviewWave.maxTasks` หรือ diff รวมเกิน `reviewWave.maxDiffLines` → ปิด wave (AC-051)
  4. เปิด wave ของ phase P เมื่อมี slot ว่าง และ (ไม่มี task ของ P ที่ `runnable`/`execution` เหลือ **หรือ** wave เต็ม)
  5. reviewer session ต่อ module ทีละตัว (claim `review/**` ชนกัน — DES-021)
- **Reviewer packet (AC-049):** session ใหม่เสมอ · `readSections` = task file ใน wave + REQ/DES ที่ task อ้าง (DES-020) · `reviewInput` (data-model): changedFiles = touchedFiles ตั้งแต่ review รอบก่อน, diffPath = `sessions/<sid>/diff.patch` (DES-021) · ไม่มี conversation/reasoning/log ของ implementer · ผล: reviewer เขียน `review\round-N.md` + แถวใน `review\index.md` แล้วคืน handoff `review` (data-model) — finding ขาดฟิลด์ (data-model) หรือ severity นอกชุด (DES-018 §Severity) → R15 (AC-050) · audit: แตะ codeRoots = violation (AC-052)
- **Rule — QA round:**
  1. ผู้สมัคร = `awaiting-qa` ใน phase เดียวกัน · รวมทุกตัว ณ ตอนเปิด (ไม่มีเพดานจำนวน)
  2. เงื่อนไขเปิด: เหมือน wave ข้อ 4 + ถ้า phase มี task ของ test-planner ที่ยังไม่ DONE → ยังไม่เปิด (AC-061)
  3. **Quiesce:** ก่อนเปิด QA round บน codeRoot หนึ่ง หยุดเริ่ม execution ใหม่บน root นั้น + รอตัวที่รันอยู่จบ · QA จบ → เดินต่อ
  4. QA session ใหม่ (ต่างจาก implementer + reviewer — AC-053) รัน check commands ของ project **ครั้งเดียวต่อรอบ** แล้วรายงาน `qa.checks[]` (command ซ้ำในรายการ = R15 — AC-054) + `qa.perTask[]` verified|blocked
  5. orchestrator เขียน Status ตาม perTask (R6/R4 — DES-018) · task PASS ไม่รอ task FAIL (AC-056) · qa-engineer ไม่เขียน Status เอง (DES-021 ข้อ 5)
  6. **🔒 (G2-f):** QA/Feature QA พบเหตุ security gate → `securityGate[] {phase, reason}` ใน handoff (state ตาม verdict — ไม่ใช้ NEEDS_HUMAN) → R23 (DES-018) · solo เขียน 🔒 เอง
- **Defect packet (AC-055):** orchestrator สร้างจาก handoff ไปไว้ `runs/<runId>/defects/<taskId>-<fixRound>.json` = `defectPacket` (ReviewFinding/QaDefect — data-model) · fix session ได้ packet นี้ + task file + REQ/DES ที่อ้าง **เท่านั้น** (ไม่แนบ conversation ของ reviewer/QA · REV-034: round file = เฉพาะไฟล์ของ finding ที่ `findings[].id` อ้าง ตาม DES-020 ข้อ 1 — ID อ้างชัดเจนตาม AC-046 · round ที่ resolve เป็น round เดียวที่ตาราง finding ชี้ ไม่รวม round อื่น)
- **Rule — Feature QA (phase = feature — OQ-13):** R18 เปิดเมื่อทุก task ใน phase verified (AC-057) · `readSections` = TP ของ phase จาก `test-plan\index.md` (ถ้ามี) **บวก** REQ/AC ที่ task ใน phase อ้าง — union (REV-035: ตรวจ AC ของ phase ครบ TP เดียวอาจไม่คลุม · ทั้งสองฝั่งมี ID อ้าง ไม่ละเมิด AC-046) · ผล `featureQa.flows[]` (data-model, AC-058) · defect ระบุ task → R4/R5 ของ task นั้น · ไม่ระบุ → R20 · security/devops ของ phase ไม่เริ่มจน Feature QA PASS (AC-057) · เขียน `qa\round-N.md` (round ใหม่, หัว `Feature QA — Phase <n>`)
- **Task Owner = qa-engineer (anchor):** **≤ 1 ต่อ phase** — > 1 → R24 · ไม่มี execution/review/qa ของตัวเอง · Depends โดยนัย = task อื่นใน phase **ยกเว้น dependents ของ anchor (ตรง/ทอด)** (+ที่เขียน — R8) · dependents ของ anchor = งานหลัง Feature QA (AC-057): `satisfied(anchor)` ⇔ phase `cleared` · พร้อม → R18 dispatch `feature-qa` (`taskIds` = [anchor], context DES-020) · ระหว่าง session step `qa` · PASS → `verified` (R19) · FAIL ระบุ task → R4/R5 ของ task นั้น + anchor `blocked`, step `waiting-deps` · ไม่ระบุ → R20 + anchor `blocked`, step `held` (`gate`, ref = phase) · ไม่นับ `fixRounds` · ไม่มี anchor → R18 เดิม · solo: qa-engineer เขียน Status anchor เอง
- **Rule — Security stage (OQ-20, AC-080):** security/reviewer **ไม่ใช่ task** (→ R24) · phase มี 🔒 ⇔ แถว Phase ใน `## Phases` มี 🔒 (PM หรือ R23) ∨ task ใน phase มี `Security-sensitive: yes` ∨ `securityGate` ใน `sessions[]` ของ phase · เปิดโดย R19 เท่านั้น = หลัง Feature QA PASS = หลัง QA ของทุก task ใน phase (R18) · 1 session ต่อ phase: kind/role `security`, `planPhase` = phase, `taskIds` = task verified ของ phase (ไม่รวมแถว R24), claim `security.md` · ผล → R21 — gate คง 7 · ไม่มี 🔒 → ไม่มี session · 🔒 ที่เพิ่มหลัง `cleared` → ไม่เปิดย้อน (แสดงบน dashboard)
- **Test Planner (REQ-018):** test-planner เป็น task ใน plan (owner test-planner) หรือ stage pre-plan ตาม trigger เดิม · เขียน `test-plan\round-N.md` · TP ทุกข้อ: `TP-NNN` + Given/When/Then + REQ/AC (AC-059) · `test-plan\index.md` มีตาราง `TP | Phase | REQ/AC | ไฟล์` (resolve — DES-020) · claim `test-plan/**` · AC-060 ดู DES-021 Security
