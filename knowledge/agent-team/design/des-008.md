## DES-008 — Human gate enforcement (7 จุด)

**Traces:** REQ-006 (AC-013, AC-014, AC-015, AC-016) · `sta2\CLAUDE.md:61-73` + `policies\agent-boundaries.md:13-23`

**Rule:** gate ทั้ง 7 ถูกบังคับโดย state machine ของ driver ไม่ใช่ความหวังว่า agent จะหยุดเอง (REQ-006 ยืนยันแล้ว): ก่อน dispatch ทุก stage และหลัง stage จบ ให้ driver evaluate gate trigger — (a) **handoff trigger:** machine handoff ของ stage ระบุ `questionsForHuman[].gate` หรือ `status: gate` (คำถามถ้อยคำตรงตัวมาจาก agent — AC-014); (b) **structural trigger:** ux-signoff = หลัง uxui-designer เสร็จ ก่อน frontend ที่พึ่ง artifact; deploy-real = ก่อน devops ขั้น "execute deploy" (devops แยกเป็น prepare → gate → execute); release-cut = ก่อนเริ่ม build phase แรก หลัง PM เสนอ `## Release Scope`; (c) **doc trigger:** plan.md `## Waiting on Human` มีรายการค้าง → run ต้องอยู่สถานะ waiting-on-human เสมอ เมื่อ gate เปิด: หยุด dispatch ทันที (AC-013 — ไม่มี process ลูกค้างเพราะ dispatch เป็นแบบ one-shot ต่อ stage), ตั้ง run.status=waiting-on-human, สร้าง GateRecord (question ตรงตัว, owner จาก gates.yaml — ตั้งต้น `jabja`, OQ-D5), แจ้ง (1) terminal — พิมพ์ banner ระบุ gate/owner/คำถาม, (2) dashboard — banner + หน้าตอบ gate เมื่อเจ้าของตอบผ่าน UI: บันทึก `answeredBy` (ผู้ตอบพิมพ์/ยืนยันชื่อเอง — ระบบไม่เขียนชื่อแทน, AC-016), `answeredAt` (นาฬิกาเครื่อง), `answer` ตรงตัว → จากนั้น (OQ-D3 ยอมรับแล้ว 2026-10-04 → design-archive.md) dispatch **record-only** ไปยัง role เจ้าของเอกสารที่เกี่ยว (เช่น business-choice → business-analyst) เพื่อบันทึกคำตอบลงเอกสารตามกติกา "Agents record them with who/when exactly as the user stated" (`sta2\CLAUDE.md:71-72`) แล้ววิ่งต่อด้วยคำตอบนั้น — คำตอบยังถูกฉีดใน brief ของ stage ถัดไปเสมอ หมายเหตุ solo mode: ไม่มี record-only run — session บันทึก who/when ลงเอกสารเองในขั้นตอนถัดไป (DES-013)

**การจับ "fail รอบที่ 3" ของ gate qa-critical:** นับจาก StageRecord ของ run (จำนวน stage ซ่อม task เดิม) ร่วมกับ qa handoff — เกิน 2 รอบ fix → gate เปิด (finish rules `sta2\CLAUDE.md:79`)
